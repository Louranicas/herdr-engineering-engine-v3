**Owner:** module owner with independent quality/security reviewer and parent integrator. **Blocking prerequisites:** Luke’s actual `start coding` instruction; scoped criteria; qualified collector and independent admission route before completion. No executable admission recipe exists now.

1. Choose the module/version/profile and dependency-ready task. Record scope exclusions, exact criteria and all 13 gate obligations.
2. Define expected behavioral cases, actual consumer signatures, fault/benign controls, budgets and acceptance measurements before implementation.
3. Assign bounded specialist work and explicit write/resource ownership. Implement only the authorized slice outside managed comments.
4. Execute ≥50 distinct qualifying primary-module cases and every applicable format/build/lint/doc/integration/security/numerical check with zero baseline warnings/errors. Retain exact raw producer results.
5. Repair/escalate failures and reverify the changed and integrated subjects; preserve missing/invalid outcomes and uncertain effects.
6. The qualified collector and reviewer admit the exact module subject only when all applicable requirements pass. A scoped v1 observation cannot perform this step.
7. Derive supported current interfaces from admitted code; record drift from desired requirements. Update README, test/migration obligations, runbooks, Justfile projections, completion views and handoff through their owners.
8. Run RB02 to publish/read back the corpus. Keep code acceptance and documentation publication as separate receipts; if publication fails, retain acceptance and repair docs without redispatching work.

**Stop conditions:** missing oracle/profile/evidence/independent admission; unresolved material findings; exceeded limits; unknown effects; unauthorized scope. **Cleanup:** each thread returns resource custody and remaining liabilities. **Completion:** exact admitted module plus verified documentation; whole-codebase release remains RB04.

### Orchestrator and specialist custody

The orchestrator owns the objective, dependency-ready slice, criteria, resource allocations and final integration. Assign implementation owners a narrow write scope; a quality/evidence reviewer owns oracle and receipt review; a security reviewer owns the actual T26/T15/T27 boundary questions; operations owns disposable package/recovery proof. These are roles, not a requirement to keep four agents or services running.

Every thread brief binds objective/criterion revision, exact source subject, owned paths/resources, allowed actions, dependencies, limits, return schema and unresolved liabilities. Shared interfaces, lockfiles and migration bytes have one writer. A waiting parent releases resources needed by children. A child success message is a candidate result; the parent must independently verify the assembled subject.

Use the existing Daybreak security profile when that specialist review is indicated. Verify actual model identity and review overrides without silently substituting models. Independent review requires a different review action and disclosed shared assumptions; merely obtaining a second signature does not authenticate a result.

### Promotion, invalidation and stop rules

- Preserve the original assessment and record each later score as a new scoped review with exact source/profile/criteria/evidence identities. Reassess only the facets supported by the new results.
- Every applicable mandatory gate must pass for the claimed module/release. Missing, skipped, stale, excluded or invalid observations remain visible. A preparation score cannot override failed acceptance.
- Re-run affected and integrated checks after source, dependency, compiler, fixture, schema, permission or deployment-profile changes. Treat automatic baseline acceptance as a defect.
- Stop a slice for unresolved ownership, unavailable oracles, unknown external effects, failed security boundaries, exceeded resources or unauthorized scope; repair or explicitly narrow the claim.
- Keep optional PyTorch/neural operators outside mandatory startup. Use T23/T24 only after simple baselines and domain-valid evidence justify their total cost.

Specify collection under T25/T26; implement and bootstrap at T06 only after original prerequisites. Read F4 and the testing standard for exact Rust/Julia recipes and intended-detector controls; neither is currently executable engine proof.
