Objective: maximize relevant, verified context and keep the full deployment corpus reachable. Read progressively; a large prompt is not proof of understanding. This workflow prepares the next authorized module task and never grants engine coding or admission. Luke must actually instruct `start coding` before engine implementation. Accepted source at its admitted revision owns implemented facts; the atlas owns intended obligations.

## Disclosure stages and exit evidence

| Stage | Read or inspect | Carry forward |
| --- | --- | --- |
| 0 · Scope and freshness | Active user instruction, applicable AGENTS.md, quick start, agreeing complete publication and graph receipts. Select exact module and original task. | Authority, root mapping, generation, task prerequisites and current implementation/admission state. |
| 1 · Module orientation | Only the selected context card, source body and module outcome. Check its question list and primary ownership. | Small intended change, current-versus-desired behavior, owned/support paths and unresolved questions. |
| 2 · Boundary closure | Relevant interface operations, API/IPC/actions, caller/callee flows, dependencies AND consumers, schemas/config/migration and original task prerequisites. | For each affected boundary: request, result/error, cancellation, usage, authority and evidence return; distinguish build dependencies from semantic flows. |
| 3 · Quality and counter-evidence | Applicable criteria/RC decisions, completion gates, testing priorities, security profile, scoped lessons and fault/benign controls. | Trace requirement → public behavior → independent oracle → intended fault → benign neighbor → raw evidence; gaps remain explicit. |
| 4 · Targeted research | Only the relevant exemplar mechanism and limits, captured Toolshed/Diary/legacy sources, primary version-specific documentation or direct upstream code needed to resolve a named uncertainty. | Exact source, section/symbol, hash/revision/date, observed fact versus inference, transferable pattern and rejected alternative. |
| 5 · Handoff and refresh | Assemble a bounded context brief; independent scout/verifier challenges coverage where warranted. Reopen changed subjects and newly implicated neighbors. | Source and relationship coverage, contradictions, unavailable tools, omitted/unread material, next original task and evidence obligations. |

An index hit, resolved seed, filename or graph edge does not establish that its source text was read. Mark each required item **read**, **located-unread**, **missing**, **access-denied**, **stale**, **unavailable tool**, **budget-omitted**, or **not applicable with rationale**. Resolve material contract conflicts through the owning record; do not silently merge incompatible versions. Budget exhaustion returns a partial brief with exact remaining reads. It is not context readiness or permission to exceed an explicit user cap.

## Context brief and stopping rule

Record in the existing task handoff or task evidence area; do not create another task/completion ledger. Include: module/task and authority; generation and exact candidate/source identities; intended change and invariants; primary owner and supporting paths; affected callers/dependencies and full return paths; selected criteria/contracts; oracle and fault/benign/mutation/security plan; actual tool availability; source locators and read status; relationship coverage; contradictions, omissions and residual unknowns; next bounded step. Account for discovery, supplement reads, repeated context and compaction, not just final packet bytes.

Context is sufficient for a particular step when its material invariants, ownership, touched boundaries and verification oracle are understood from identified sources, and no unresolved gap could change that step’s safe design. This is a documented engineering judgment, not a new automatic readiness gate. If uncertainty changes the design, follow the exact deeper branch. Avoid repeated whole-corpus reads without a new question. Preserve full-corpus access through the card inventory even when its content is omitted from the current packet.

## Iteration and end-to-end closure

Scout → explain the intended change and oracle → implement only when authorized → verify on exact subjects → investigate failures and read newly implicated context → repair/reverify → independent module admission → parent integration/release proof → synchronize source-derived facts and corpus → refresh affected context cards and handoff. A changed interface/schema/config/fixture/toolchain invalidates the relevant earlier brief and evidence; trace both consumers and dependencies, including cross-cluster return paths. Keep other writers quiescent during publication.

The card directory is rendered from existing module/task/flow/facet owners plus module_context.py reading questions. To update the skill, edit the atlas agent-skills/hee-module-scout source, validate it, publish its code/vault copies, then refresh the installed personal copy and verify byte parity. Installation is an explicit documentation action; it is not a runtime skill deployment. No new automatic watcher or scheduler is introduced.
