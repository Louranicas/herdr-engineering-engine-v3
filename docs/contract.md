# T01 — initial task and release contract

Status: implementation candidate under Luke's actual `start coding` instruction
on 2026-09-15, followed by authorized zero-touch implementation/deployment.
T01 remains open pending the integrated foundation check. This authored contract
follows RC01 revision 3 and preserves the module admission requirements.

## Release charter and first workload

The first supported design profile is `rust-library-change/1`: one contained
offline Rust library change for the local operator. Inputs are an immutable
source snapshot, an explicit task, an independent oracle and a protected
criterion set. Output is a candidate patch, explanation and behavioral evidence.
One library, at most three authored source/test files and 200 changed logical
lines bound each candidate workload. These workload bounds do not describe the
size of the engine implementation itself.

`WL-U64-PARSE-001/v1` is the first development workload: parse a borrowed UTF-8
string containing `0` or `[1-9][0-9]*` into a u64. Error precedence is empty,
invalid character anywhere, noncanonical leading zero, then overflow. No
normalization is permitted. The shared engine scalar implementation now exercises
the same specified semantics. The actual disposable fixture now exists in
[WL-U64-PARSE-001/v1](../evaluation/tasks/WL-U64-PARSE-001/v1/TASK.md), with a
frozen manifest, faulty baseline, reference patch and separately authored oracle.
The ordinary authoring filesystem supplies no hostile oracle protection.

Data must be public synthetic or explicitly classified operator-owned
`local_private`; the initial profile makes zero external requests and spends zero
external currency. Candidate work cannot alter dependencies, policy, verifier,
lockfiles or build hooks, merge changes, deploy or contact providers.

The release target remains RC02 `fedora44-x86_64-local/1`, Rust 1.98.0/edition
2024 with the pinned Julia/Pi/SQLite tuple. Toolbx is the authoring/build layer.
The current tests are dependency-free development checks, not packaged runtime
qualification. T25 owns the actual project build manifests and quality matrix.

## Current callable candidate surface

- `contracts::parse_u64_decimal`, `U64Decimal`, `U32Decimal`, `Generation`,
  `UuidV4` and `Sha256Digest` provide pure scalar validation. They allocate no
  input buffers. Acquisition must be bounded by the future transport owner before
  parsing. Generations are nonzero and advancement fails on overflow; UUID/digest
  validity carries no authority. No JSON codec or hash computation is claimed.
- `task::LoopGuard` binds 1–64 criteria and one initial attempt generation to the
  fixed 1,200-second task window. Candidate work must begin before 900 seconds,
  allowing the final 300 seconds for verification/cleanup. At most three attempts
  may begin; only one may be outstanding. Two consecutive attempts without a new
  independently satisfied criterion stop new work. Repeated criteria are not
  progress. Its progress history is explicitly unsuitable for current-subject
  acceptance.
- `begin_attempt` returns a generation or a typed refusal. Reconciliation must
  match the active generation, use only declared criteria and preserve monotonic
  time. Cancellation and unresolved authority/effects block subsequent starts;
  late observations remain recordable. These are in-memory decisions. The future
  task/store/check/worker owners must authenticate observations, persist state,
  enforce resource limits and establish actual settlement before applying them.

## Ownership, boundaries and completion predicate

The existing 22-module graph remains unchanged. `contracts` owns shared types;
`task` owns task/attempt policy; `store` owns durable transactions/outbox;
`budget` owns usage/reservations; `worker` owns execution and descendants;
`check` owns independently collected criterion evidence; `app` assembles them.
Task-to-contracts is the only compiled production dependency in this slice.

The 21 action IDs, closed request/result/error bodies, generation preconditions,
principal-scoped idempotency selector, readback and frame bounds remain specified
by [RC03](contract-decisions.md#rc03--versioned-control-and-rustjulia-contracts).
Their structural schema now exists in
[control-v1.schema.json](../schemas/actions/control-v1.schema.json), generated
deterministically by its adjacent authoring script. The retained request action
selects the exact result schema; empty list results can share the same shape.
Framing, UTF-8 byte limits, duplicate-key detection, identity correlation,
authorization and effect truth require the future typed runtime. Codecs and
CLI/UDS/worker integrations remain unimplemented. Future request/result/error/cancel/usage/evidence return paths
are the F01–F19 routes in [the task context card](module-context/task.md).

Completion requires current-subject evidence for every mandatory criterion,
matching source/generation/acceptance/fixture/profile identities, authentic
collector custody, no unresolved effects or cleanup, preserved cancellation
ordering, independent admission and the integrated parent check. Child success,
checker success and historical progress are insufficient. This slice exposes no
operation that marks a task accepted. T04/T06/T07 retain durable loop integration;
the qualified admission collector remains unavailable.
