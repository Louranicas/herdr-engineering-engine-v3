# Quality, uncertainty and deeper module resources

Read the selected module card’s verification focus, then the exact controlling records. Do not preload every standard or treat a requirement as an available command.

## Sources of quality obligations

- `corpus/testing-standard.json`: selected module priorities; ≥50 meaningful distinct primary-owned cases; zero baseline warnings/errors; assimilation and mutation conventions.
- `corpus/public-interfaces.json`: selected public operation, caller contract, version/compatibility/error/cancellation semantics.
- `corpus/completion-standard.json`: universal gates and the module’s concrete outcome, integrated scenario, fault/benign controls and complexity boundary.
- `corpus/readiness-convention.json`: applicable facet/criterion and selected RC decisions; primary ownership differs from broad applicability. R90 packages are work groupings, not new task dependencies.
- `corpus/security-profile.json`, RB05 and T26/T27: requested/effective reviewer identity, threat scope, protected collector evidence and finding disposition. Follow the existing model-selection procedure; do not guess model availability or execute composer commands in Bash.
- `corpus/learning-register.json`: scoped trigger, antipattern, known good pattern, counterexample, capture identity and transfer limits.

Use the card’s links to the native counterparts and atlas owners. Accepted source/schema at the admitted revision owns implemented behavior; desired contracts remain normative. Source presence or an exemplar test does not demonstrate admission.

## Tool and oracle discipline

Rust formatting, pedantic Clippy, build/lint/doctest/test profiles; Julia Test, logging/Broken handling and package checks; Bash/Pi literal argument, error, cancellation and reload cases; SQL durability/migration/recovery; and module-specific fault/mutation/security checks must use the selected real toolchain and controlled fixtures when implemented. A compiler/test process can run candidate-controlled build scripts or hooks. Inspect the qualified threat boundary and authorized effects before execution. Current engine validators and admission collectors remain unavailable.

For each consequential check define a valid passing baseline, intended behavior-breaking fault, independent expected refusal and a benign near-neighbor where false positives matter. Formatting rejection of a mutant does not prove the behavioral detector. Bind exact source/config/profile/fixture/tool identities to raw receipts, retain missing/excluded/unmeasured cells and repair/reverify changed subjects. Do not lower standards, suppress warnings globally or create superficial cases merely to reach 50.

## When deeper research is needed

Follow the selected exemplar’s mechanism, source files, scoped verification receipt and production limits. Its Toolshed, Diary, Zellij/ORAC and other codebase captures are lessons with dated identities; adopt only the component that resolves the current design question. Use current primary docs or inspected pinned upstream code for unstable API/toolchain facts. Preserve contradictions rather than selecting the most convenient source.

For numerical/Julia/routing work, optional PyTorch/neural operators require domain justification, a simpler baseline, leakage-resistant split policy, immutable dataset identity, units/shapes/tolerances, uncertainty, reproducibility and resource/dependency evidence. A numerical report cannot write leases, grants or accepted state. Ask what the system measures, what it cannot observe, and how stale/missing/adversarial inputs, non-human consumers, constrained resources and maintenance costs affect the result. Do not equate model confidence, agent consensus or fluent prose with proof.

If a material uncertainty remains, name the exact missing fact, its owner and a bounded research or fixture step. Continue unaffected authorized work. After actual module/integration qualification, refresh the corpus and context routes through the existing update protocol; skill use never substitutes for proof of completion.
