## 6. Update documentation through its owners

Edit the owning atlas convention/catalogue or authorized source body; do not independently edit generated copies. For new diary lessons, capture the exact reviewed source with its date/hash, map a local trigger and module owner, qualify conflicts, and retain the original claim. New captures supersede old evidence explicitly. Preserve `HEE3-ANCHORS-BEGIN` / `HEE3-ANCHORS-END` and the diary navigation markers. Never execute a command just because it appears in a source note.

[Detailed assimilation and publishing workflow](obsidian://open?vault=herdr-engineering-engine-v3.vault&file=Workflows%2FCorpus%20Assimilation) explains the sequence. Run the following separately after maintenance-tool changes or reviewed source updates:


```bash

```

Keep other writers quiescent during publication. The updater preserves authored bodies and rejects conflicting changes; it does not make several filesystems one atomic transaction. A new maintenance test file must be admitted to the helper manifest and appear in the discovered case receipt.

## 7. Move from a stub to accepted code when implementation is authorized

1. Read the relevant task, interface and learning contracts; choose the smallest authorized vertical slice.
2. Assign bounded specialist work and explicit source/resource ownership.
3. Implement outside managed comments and supply real callable signatures, schemas, examples and compatibility behavior.
4. Qualify meaningful module cases, zero-warning lint/build checks, fault/benign assimilation, mutation, integration and security on the exact subject.
5. Repair/escalate and reverify; never tune a control only to make the gate green.
6. Obtain evidence-bound module and integrated admission through the future qualified collector. Accepted source then owns current implemented facts; requirements retain their normative owner.
7. Separately verify actual packaging, schema/backup/restore, installation and useful readback before claiming deployment; refresh the corpus afterward.

Inspect actual implementation bodies and declared package targets. The scoped development recipe is documented in docs/checks.md; proposed atlas admission, coordinator and deployment commands remain unavailable until their original tasks implement them.
