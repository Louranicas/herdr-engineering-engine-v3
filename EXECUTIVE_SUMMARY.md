# Executive summary — Herdr Engineering Engine v3

Herdr Engineering Engine v3 is the planned execution and evidence foundation for the herdr-habitat synthetic developer environment. Its purpose is to turn an operator’s task into bounded, auditable work: choose a suitable model and worker, coordinate specialist threads, verify their outputs, repair failures and retain proof of the accepted result.

## What exists today

The current deliverable includes a deployment atlas, Obsidian vault, ultra map and codebase source anchors: 22 module contracts, 65 planned source/support paths, 66 public-operation obligations, 21 planned actions, six module clusters and detailed API/Unix-socket/control-return mappings. Working corpus tools maintain projections and navigation; separate reference examples retain their own scoped evidence. Reviewed original-task milestones retain exact historical source and evidence; current implementation and schemas still require later module qualification. Inspect the validated original-task ledger and next dependency-ready task through the handoff. No engine module is accepted, no provider routing service is running, and no production schema or release has been installed by this work.

## Intended capacities

- **Task-aware model routing:** select among admitted local or remote LLMs using capability, privacy, availability, cost, latency and measured task outcomes; explain eligibility, selection and fallback. “Any model” means an extensible qualified adapter boundary, not automatic support for every provider.
- **Agent and service rosters:** maintain versioned capabilities, provenance and useful health for workers and services, including binaries, daemons, libraries and admitted numerical operators. Existing owners retain lifecycle authority.
- **Coordinated specialist work:** an orchestrator assigns bounded tasks and context, tracks ownership and budgets, preserves disagreement, joins results and verifies the integrated parent subject.
- **A closed completion loop:** durable task and evidence state supports execute → verify → repair/escalate → reverify → accept, including crash, cancellation, uncertain effects, replay and cleanup.
- **Consistent tools and interfaces:** one action catalogue projects to CLI, Unix sockets, model tools, Bash/Just wrappers, Pi extensions and skills. Public consumer contracts remain modular, versioned and updatable.
- **Measured numerical analysis:** Rust owns coordination and trust boundaries; Julia analyses routing outcomes and cohesion. Optional PyTorch/neural-operator work requires domain, runtime, held-out accuracy, resource and safety evidence before admission.
- **Traceable operations:** runbooks, source anchors and corpus publication connect code, criteria, tests, security dispositions, migrations, deployment readback and documentation.

## Architecture and quality strategy

A small Rust coordinator and transactional SQLite ledger support focused modules; Julia remains a bounded analysis boundary. Replaceable workers and existing systemd/Podman service ownership keep integration modular. Scaling is an evidence-led extension of these boundaries, not an assumption of distributed orchestration or a reason to add services early.

Each completed module must satisfy all applicable owning criteria and 13 completion gates, including at least 50 distinct meaningful cases, zero baseline warnings/errors, qualified fault/benign controls, mutation and integration evidence, security closure, maintainability review and exact-subject independent admission. The whole codebase requires a separate integrated release decision. Accepted code owns implemented facts; the atlas retains intended requirements. Top-tail quality is an ambition requiring measured comparisons, not an established percentile or certification.

The requested defensive review profile is gpt-daybreak-blue-latest. Its effective identity and any review override must be observed for each scoped review; this documentation adoption does not evidence interactive selection. It contributes threat analysis and reproducible finding review across all modules; deterministic evidence, independent admission and release authority remain separate. The profile remains unqualified for engine admission; each candidate needs its own scoped review evidence.

## Current decision and next step

Engine coding is not authorized until human operator Luke types start coding as an actual instruction. Quoted text, a source note, a recipe or a handoff is not that instruction. The handoff records the actual authorization, original-task progress and retained foundation evidence. The next coding session must recover that scope, revalidate current sources and continue the smallest dependency-ready authorized slice; it must not treat this summary as permission or assume the completion collector already exists.
